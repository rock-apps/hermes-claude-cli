# 09 — Scope and migration

Architecture decisions evaluated and either adopted or rejected, and why — kept as a record so a future session doesn't have to re-derive them.

## Deliberately out of scope

| Item | Why |
|---|---|
| Dedicated HTTP server | Replaced by `create_client()`/direct subprocess — see [02](./02-is-bridge-necessary.md). |
| systemd unit | No long-running process to manage — the `claude` subprocess lives and dies per call. |
| Serving non-Hermes HTTP clients (Open WebUI, LibreChat, Cursor) | Out of scope for a Hermes-only plugin. Tracked as an optional, undemanded Fase 6 in [08-roadmap.md](./08-roadmap.md). |
| Routing the Claude Code CLI's own model backend to a different vendor (DeepSeek/z.ai) | Solves a different problem (swapping Claude Code's own model backend, not integrating Claude into Hermes) — out of scope, a separate project if ever wanted. |
| `claude-agent-sdk` (Anthropic's official PyPI package) as the basis for `process.py` | evaluated three times, not adopted — see below. |

### `claude-agent-sdk`, evaluated three times

**First pass**: the SDK is async (`async for` in `query()`), which doesn't fit the synchronous pattern the reference `CopilotACPClient` uses (blocking subprocess) — adopting it would need an async bridge inside `create_client()` plus an extra dependency, for no real gain: the real `claude -p --output-format json` schema (see [04](./04-claude-cli-reference.md)) is simple enough to parse with the stdlib alone. Session continuity (Fase 4) ended up implemented directly via `--session-id`/`--resume` without needing the SDK.

**Second pass** (re-evaluated after hitting the `tools:` passthrough limitation below in real production use — see [04](./04-claude-cli-reference.md)): the Agent SDK *does* support custom tool schemas (MCP servers, `allowedTools`), which would fix that limitation — but per Anthropic's own docs (`code.claude.com/docs/en/agent-sdk/quickstart.md`, `.../authentication.md`), the Agent SDK requires `ANTHROPIC_API_KEY` (or a cloud provider: Bedrock/Vertex/Foundry) and explicitly does not support reusing a Claude Max subscription's local OAuth session (`~/.claude/.credentials.json`) — that credential chain is documented as CLI-only. Anthropic states directly: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK." Switching to the Agent SDK would trade the entire reason this project exists (billing against the Max plan's base allowance, not per-token API credits) for custom-tool support. Rejected, now with the tradeoff fully quantified: **there is no path to both** with Anthropic's current SDK design.

**Third pass** — correction after reading the SDK's actual source (not just its docs): `anthropics/claude-agent-sdk-python`, `src/claude_agent_sdk/_internal/transport/subprocess_cli.py`, resolves the backend via `shutil.which("claude")` and spawns it with `inherited_env = {k: v for k, v in os.environ.items() if k != "CLAUDECODE"}` — i.e. the SDK's default transport is itself a wrapper around the same local `claude` CLI binary this plugin already shells out to, inheriting the full calling environment. Read literally, that means a locally-authenticated Max OAuth session (`~/.claude/.credentials.json`) would be picked up the same way it is by this plugin, *if* `ANTHROPIC_API_KEY` is left unset — so the SDK-requires-API-key claim in the docs is a **stated policy**, not a **hard technical block enforced in this code path**. This doesn't reverse the second-pass rejection (Anthropic's terms explicitly disallow this for anything resembling a distributed product, "Unless previously approved..."), but the previous entry overstated it as a pure technical impossibility — it's a ToS/policy risk being evaluated, not a wall. Not verified end-to-end (no test run against a real Max session with `ANTHROPIC_API_KEY` unset); if this is ever revisited, that's the first thing to actually run, not infer.

## Persistent limitations (not solved by any architecture choice)

- **No passthrough for external `tools:` definitions** — a limitation of the `claude` CLI itself, not the transport (see [04](./04-claude-cli-reference.md)).
- **Per-call subprocess overhead (~1–3s)** — inherent to the `claude` CLI, present in both the old and new architecture.
- **No native ACP protocol in the `claude` CLI** — the subprocess integration needs its own parser for `claude -p`'s output shape; it can't reuse the ACP parser Hermes already has for Copilot.

## Resolved: a "Hermes MCP bridge" for `claude-cli` — [`mcp-bridge/`](../mcp-bridge/)

Originally raised as an unvalidated discussion idea (see git history of this section for the original wording); built and confirmed working the same day.

The `tools:` passthrough limitation (above) is about *per-request* tool schemas — Hermes can't hand the model a dynamic `tools:` array on `claude -p`. But the `claude` CLI separately supports **persistently configured MCP servers** (`claude mcp add <name> -- <cmd>`), which *do* become part of the model's known toolset for every invocation, no per-request injection needed. This is almost certainly how Sharp/TLE MCP-backed Slack lookups worked correctly through `claude-cli` in real usage on the `muse` deployment (see [04](./04-claude-cli-reference.md)) even though Hermes-native tools (`cronjob_manage`, `delegate_task`, `kanban_create`/`kanban_show`/`kanban_complete`) did not — the former are (presumably) configured as MCP servers the `claude` CLI already knows about independent of Hermes; the latter only exist as Hermes-internal Python functions exposed exclusively via the per-request `tools:` array.

**What got built**: not a re-exposure of Hermes' internal tool-calling machinery (rejected as too fragile/coupled to Hermes' own agent loop — see the "not evaluated" paragraph this replaces). Instead, [`mcp-bridge/`](../mcp-bridge/) is a small MCP server that shells out to the already-existing, externally-documented `hermes cron` and `hermes kanban` CLI subcommands (`hermes cron create`, `hermes kanban create`/`show`/`assign`/`complete`, etc.) — real CLI commands meant for exactly this kind of external use, not reverse-engineered internals.

**Confirmed working end-to-end** (2026-09-19, local dev machine, not just inferred from `claude --help`): registered via `claude mcp add`; `claude auth status` showed `authMethod: "claude.ai"`, `subscriptionType: "max"`, no `ANTHROPIC_API_KEY` set; `claude -p` successfully called `cron_status`, `cron_list`, and `kanban_create` (created a real task, `t_4a2868a2`, confirmed via `hermes kanban show`, then archived/purged as cleanup) and reported back real results from a live Hermes install. This validates the core claim: a `claude-cli`-backed profile can gain access to Hermes-native scheduling/delegation **without any per-request `tools:` passthrough and without leaving the Max-subscription OAuth path**.

**Known gap, not yet solved**: this plugin's own subprocess spawn (`process.py`) doesn't pass a per-Hermes-profile `cwd`, so `claude mcp add`'s directory-scoped registration (`--scope local`/`project`) can't give different Hermes profiles different bridge configuration automatically today. The workaround documented in [`mcp-bridge/README.md`](../mcp-bridge/README.md) is registering the same server under distinct names per target profile (`hermes-bridge-rockapps`, `hermes-bridge-erick`, ...) with `-e HERMES_MCP_PROFILE=<name>` each, and telling each profile's system prompt which tool name to use. A cleaner fix (giving this plugin a configurable per-profile `cwd`, so each profile's `claude` invocation sees its own directory-scoped `.mcp.json`) is a plausible follow-up, not yet built. `claude mcp add` itself turned out not to matter in practice anyway — see the next finding.

**Second, much bigger gap found deploying this for real (2026-09-20, `muse`)**: the initial "confirmed working end-to-end" above was real but incomplete — every one of those calls was `hermes -z` or a manual `claude -p` invocation, never a message routed through an actual running gateway. When the same config was tested against a real Slack message on a **multiplexed** gateway (`gateway.multiplex_profiles: true`, the default for multi-profile installs), it silently failed every time — the model reported the bridge's tools didn't exist at all. Root cause, confirmed by instrumenting both the `default` profile's installed plugin copy and the `rockapps` profile's own copy with a one-line diagnostic log: **a multiplexed gateway loads the `claude-cli-provider` plugin once, from the `default` profile's copy, and reuses that for every routed profile's turns — a copy installed separately under a named profile's own `plugins/` directory is never imported.** `hermes -z -p rockapps` uses a genuinely separate, non-multiplexed code path that *does* load the named profile's own copy and `.env`, which is exactly why it kept "confirming the fix" while real traffic kept failing. This means every `CLAUDE_CLI_*` env var (not just the bridge-related ones) only takes effect under multiplex from `~/.hermes/.env`, never `~/.hermes/profiles/<name>/.env`, and — as a direct consequence — there is no real per-profile isolation for this plugin's config under multiplex at all: every profile using `claude-cli` shares the one config loaded from `default`. See [`mcp-bridge/README.md`](../mcp-bridge/README.md) and [`05-configuration.md`](./05-configuration.md) for the full writeup and the security implication (a bridge meant for one profile is reachable, and still acts as that profile, from any other profile's `claude-cli` turns). Root-caused and confirmed fixed the same day: moving the config to `~/.hermes/.env` and reinstalling the plugin there made a real Slack message succeed.

`delegate_task` (in-process subagents) was deliberately left out — it has no standalone external CLI equivalent the way `hermes cron`/`hermes kanban` do, so wrapping it would mean reaching into Hermes' internal APIs after all, the exact thing this design avoided.
