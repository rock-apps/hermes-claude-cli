# 08 — Segurança

## Modelo de ameaça: antes (bridge HTTP) vs. depois (subprocesso direto)

| Vetor | `claude-bridge` original | Arquitetura unificada (subprocesso via `create_client()`) |
|---|---|---|
| Rede | Servidor HTTP em `:9180` sem autenticação, e o bind real é `0.0.0.0:9180` (não `127.0.0.1`, apesar do README dizer o contrário — ver [01](./01-analise-claude-bridge.md)). Qualquer processo com acesso à porta gasta a assinatura do usuário. | **Nenhuma porta aberta.** O único canal é stdio de um subprocesso filho do próprio processo do Hermes. Não há superfície de rede a proteger. |
| Processo persistente | Roda 24/7 como serviço systemd, mesmo sem uso — janela de exposição contínua. | Subprocesso existe apenas durante a chamada (ou durante a sessão, em v2) — janela de exposição mínima e delimitada. |
| Acesso a filesystem | Opção "fácil" documentada é `--dangerously-skip-permissions` = acesso total ao filesystem do usuário. | Mesmo risco existe se configurarmos o modo de permissão errado — **não é eliminado pela mudança de transporte**, precisa de decisão explícita (ver abaixo). |
| Execução de comandos (Bash) | O `claude` CLI, por padrão, tem a ferramenta Bash disponível — um provider headless pode acabar permitindo que o modelo rode comandos de shell arbitrários "em nome" de uma chamada de chat comum do Hermes, sem o usuário perceber. | **Resolvido na Fase 3**: `CLAUDE_CLI_RESTRICTED` default `true` — `--restricted` (remove Bash/PowerShell/REPL/WebFetch) vem ativado por padrão. Confirmado empiricamente que não quebra chat comum (pergunta simples respondida normalmente) e que de fato bloqueia uma tentativa explícita de usar Bash ("I don't have access to a Bash tool in this session"). Setar `CLAUDE_CLI_RESTRICTED=false` para quem quer o provider como agente completo com acesso ao sistema. |
| Vazamento de variáveis de ambiente | O bridge documenta o risco ("Subprocesses inherit the bridge's env. Don't put untrusted env vars in the systemd unit.") mas não faz nada a respeito. | **Corrigido na Fase 3** — `process.build_subprocess_env()` usa allowlist (nega por padrão): só `HOME`, `PATH`, `LANG`/`LC_*`, `TERM`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL` passam para o subprocesso; tudo mais do ambiente do Hermes é descartado. |
| **`ANTHROPIC_API_KEY` sobrescreve a autenticação OAuth/Max** (achado durante a Fase 3, não estava previsto) | N/A — não documentado, não testado no projeto original. | Verificado empiricamente: se `ANTHROPIC_API_KEY` estiver presente no ambiente do processo pai (ex.: porque o provider nativo `anthropic` do Hermes precisa dela) e for repassada ao subprocesso `claude`, o CLI avisa "another auth source is set and takes precedence over your claude.ai login" e tenta faturar pela API key em vez da assinatura Max — **isso quebraria o propósito inteiro do projeto silenciosamente**. A allowlist de `build_subprocess_env()` acima já resolve isso por construção (nunca repassa `ANTHROPIC_*`), mas fica registrado aqui porque é o motivo concreto pelo qual a filtragem de ambiente é allowlist e não uma tentativa de "lista de variáveis perigosas para bloquear" (abordagem frágil — teria que adivinhar `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, futuras variáveis ainda não lançadas, etc.). Testado com uma chave inválida propositalmente no ambiente pai: sem a correção, a chamada trava/erra; com a correção, funciona normalmente via OAuth. |
| Redação de conteúdo sensível | Inexistente no bridge original. | O `copilot_acp_client.py` de referência usa `redact_sensitive_text()` antes de devolver conteúdo lido do filesystem. Avaliar se o `claude` CLI já faz proteção equivalente nativamente (provavelmente sim, dado que é o mesmo produto Anthropic que já implementa proteções de leitura) — item a validar na fase de implementação, não assumir sem checar. |
| Custo/gasto descontrolado | Sem teto de gasto por chamada. | `--max-budget-usd` disponível nativamente no CLI (ver [06](./06-referencia-cli-claude.md)) — deve ser exposto como configuração, não é usado por padrão hoje. |

## Decisão tomada: modo de permissão padrão (Fase 1 + Fase 3)

Havia duas opções — restritivo por padrão vs. permissivo espelhando o `claude-bridge` original (`--dangerously-skip-permissions` sempre). **Optou-se pela restritiva**, implementada em duas partes:

1. `CLAUDE_CLI_PERMISSION_MODE=auto` (Fase 1) + `--permission-prompts none` sempre — nada que pediria confirmação humana trava esperando input; é negado.
2. `CLAUDE_CLI_RESTRICTED=true` por padrão (Fase 3) — remove Bash/PowerShell/REPL/WebFetch. Confirmado empiricamente: não quebra chat comum, e de fato bloqueia uma tentativa explícita de usar Bash.

`permissions.bypass` (`--dangerously-skip-permissions`) continua existindo em `process.PermissionConfig` para quem quiser espelhar o comportamento do bridge original, mas **não há variável de ambiente exposta para ativá-lo** — é opt-in só via código (passar `PermissionConfig(bypass=True)` diretamente), não uma flag de configuração de produção. Quem quiser esse modo hoje precisa editar `client.py` intencionalmente, o que é deliberado: não queremos que seja tão fácil quanto `CLAUDE_BYPASS_PERMISSIONS=true` era no original.

## Bug real encontrado e corrigido: `--add-dir` engolindo o prompt

`--add-dir` no CLI `claude` é uma flag variádica (aceita múltiplos valores). Verificado empiricamente: `build_args()` gerava `[..., "--add-dir", "/dir1", "--add-dir", "/dir2", prompt]` sem separador, e se `prompt` não começa com `-` (o caso comum), o CLI o consumia como **mais um diretório** da lista de `--add-dir`, em vez de reconhecê-lo como prompt — resultando em `Error: Input must be provided either through stdin or as a prompt argument`. Isso só se manifestava quando `CLAUDE_CLI_ALLOWED_DIRS` estava configurado (default é vazio, por isso não apareceu nos testes/smoke tests anteriores). Corrigido inserindo `--` (fim de parsing de opções, suportado pelo CLI) antes do prompt, incondicionalmente — não só quando há `allowed_dirs`, para blindar contra qualquer flag variádica futura. Testado de verdade com `CLAUDE_CLI_ALLOWED_DIRS` configurado após a correção — funciona.

## Revisão: redação de conteúdo sensível

Testado empiricamente: o `claude` CLI **não redige** segredos de arquivos quando explicitamente instruído a imprimir o conteúdo bruto (testado com uma chave de API e uma senha de banco de dados fake num arquivo, via `--add-dir` + prompt pedindo o conteúdo exato — ambos vieram de volta sem redação). Diferente do `copilot_acp_client.py` de referência, que consegue redigir porque ele **medeia** o acesso a arquivo (implementa o handler `fs/read_text_file` do protocolo ACP e intercepta o conteúdo antes de devolver ao modelo) — nossa arquitetura de subprocesso não tem esse ponto de interceptação: o `claude` CLI lê arquivos inteiramente dentro do seu próprio processo, usando sua própria ferramenta Read, sem nos consultar. A única redação possível no nosso caso seria "raspar" padrões de segredo do texto final de resposta antes de devolver ao Hermes — uma proteção mais fraca (não impede o modelo de já ter "visto" o segredo durante seu raciocínio) e com risco real de falsos positivos (corromper uma resposta legítima que mencione, por exemplo, um formato de exemplo de chave de API). **Decisão**: não implementar essa raspagem de saída por enquanto — documentar como limitação aceita, não uma omissão. Se isso vier a importar (ex.: o provider processando arquivos de terceiros não confiáveis), reavaliar como funcionalidade own, opt-in, separada.

## Itens de hardening para o roadmap (não bloqueiam v1, mas devem ser rastreados)

- Confinamento de paths (`_ensure_path_within_cwd` no `copilot_acp_client.py` de referência é um bom modelo) caso o plugin precise manipular paths recebidos de fora antes de repassar ao CLI.
- Auditoria de log: o bridge original loga `model`, contagem de mensagens e tools por request — manter esse nível de observabilidade (sem logar conteúdo de prompt completo, que pode conter dados sensíveis do usuário).
- Revisão do que acontece se múltiplas chamadas concorrentes tentarem usar o mesmo `--session-id` (v2) — condição de corrida potencial a testar antes de habilitar sessões contínuas por padrão.
